# Does kloak hide how I type?

*4 November 2026. Numbers and code: [research/results/2026-11-04-kloak](../results/2026-11-04-kloak/README.md).*

The way you type identifies you. Hold times and the gaps between keys are
stable enough per person that a web page measuring them in JavaScript can tell
users apart, and the idea keeps coming back in the news as "the end of
anonymity". The standard answer is kloak, a small Linux daemon that sits
between the keyboard and the applications and adds a random delay to every
event. I build a tool whose whole job is to recognise a typist, so I wanted
to know two things: does kloak actually defeat recognition, and can an
observer filter its noise back out?

Short answer: kloak blurs a single short sample well, and it does not survive
averaging. Its noise has a mean of zero and does not depend on who is typing,
which is exactly the kind of noise that averaging removes. A couple of hundred
keystrokes are enough to get back to where an observer without kloak starts.

## What kloak does

kloak grabs the input device, so that nothing else reads it, and re-emits
each event later. The original version (github.com/vmonaco/kloak, John Monaco)
re-emits through a virtual `uinput` keyboard; the maintained version
(github.com/Whonix/kloak) speaks the Wayland virtual-keyboard protocol and
works only on wlroots-based compositors such as Sway; GNOME's compositor
does not offer the virtual-pointer protocol it relies on.

The whole obfuscation is three lines, the same for key events in both
trees (the original also releases its synchronisation reports at the lower
bound, with no extra draw):

```c
lower_bound = min(max(prev_release_time - current_time, 0), max_delay);
random_delay = random_between(lower_bound, max_delay);
ev_packet->sched_time = current_time + random_delay;
```

Every event is delayed by a whole number of milliseconds drawn uniformly
between a lower bound and `max_delay`. The lower bound is how long the
previous event still has to wait: an event is never released before the one
that came before it, so the order of keys is preserved and the lag never
exceeds `max_delay`. Both READMEs give 100 ms as the default. The original's
source actually sets `DEFAULT_MAX_DELAY_MS` to 20, so a build of that tree
without `-d` runs at 20 ms.

## What that noise looks like

Take two consecutive key presses, delayed by `u1` and `u2`, both uniform on
[0, D]. The measured gap is the true gap plus `u2 - u1`. That difference is
triangular on [-D, D], centred on zero, with a standard deviation of
D / sqrt(6): 41 ms at the default 100 ms. A hold time is affected the same
way. The order constraint only changes this when a true interval is shorter
than the pending delay, which pushes short intervals up a little.

I checked the arithmetic against the corpus. At D = 100 ms, the measured
added deviation on key-to-key latencies is 40.4 ms and the mean shift is
0.04 ms. A small bias only appears at 200 ms (holds gain 8 ms on average), when
clamping starts to matter.

Two consequences follow before any experiment. First, the noise is large
next to hold times (29 ms of natural spread between repetitions on CMU) and
small next to latencies (186 ms), so kloak mostly wipes out holds. Second, a
zero-mean noise that is the same for everyone can be averaged away: the mean
of n noisy gaps has its noise divided by sqrt(n), and the true mean, which is
the person's signature, stays where it was.

## How I measured it

I used the CMU keystroke benchmark (Killourhy and Maxion 2009): 51 people
typing the same password `.tie5Roanl` 400 times, with hold and latency
columns. I rebuild each repetition as its 22 key events, pass them through a
faithful model of kloak's schedule, and read the columns back. Every
repetition gets its own random draw, and the run is seeded.

The protocol is the published one: for each person, train on the first 200
repetitions, test on the last 200 as genuine and on the first 5 repetitions of
each of the 50 others as impostors. Two readings: verification EER (the error
rate where false accepts equal false rejects), and identification, the share
of test samples whose nearest template belongs to the right person among 51
(chance is 2 %). The detector is scaled Manhattan, the classic baseline for
this corpus; without kloak it gives an EER of 0.0960, which matches the
published 0.096.

Three observers:

1. **Profiled before kloak.** It holds a template of me taken without kloak,
   then sees me with kloak on.
2. **Aware of kloak.** It trains on obfuscated samples. It does not need to
   catch me under kloak for that: the algorithm is public, so it can push my
   old clean samples through the same schedule.
3. **Aware and patient.** Like 2, but it averages each feature over k
   consecutive repetitions before matching, which anyone holding more than one
   login's worth of typing can do.

## Results

At the default 100 ms, against a single repetition (11 keys):

| Observer | EER | Identification |
|---|---|---|
| No kloak | 0.096 | 48 % |
| Profiled before kloak | 0.166 | 13 % |
| Aware of kloak | 0.152 | 22 % |

On one short sample, kloak does its job. Identification drops by half to
three quarters depending on the observer, more than the 20 to 30 % reduction
the project quotes, probably because a password is a very short sample.

Now let the aware observer average over k repetitions:

| D | k = 1 | k = 5 | k = 10 | k = 20 |
|---|---|---|---|---|
| none | 0.096 / 48 % | 0.072 / 65 % | 0.061 / 70 % | 0.048 / 75 % |
| 100 ms | 0.152 / 22 % | 0.113 / 48 % | 0.090 / 58 % | 0.062 / 68 % |
| 200 ms | 0.185 / 15 % | 0.158 / 33 % | 0.131 / 43 % | 0.098 / 52 % |

(EER / identification.) With 20 repetitions, 220 keystrokes, an observer
facing kloak at its default does better (0.062, 68 %) than an observer facing
no kloak at all on a single sample (0.096, 48 %). The break-even with that
clean single sample comes between 5 and 10 repetitions, 55 to 110 keystrokes.
Doubling the delay to 200 ms, which is a lag you feel, only pushes it to about
20 repetitions, 220 keystrokes. At 25 or 50 ms, the settings that are pleasant to type with,
averaging over 20 repetitions removes kloak's effect entirely: the numbers
match the clean column within noise.

So yes, the noise can be filtered, and the filter is the most boring one
there is. No knowledge of the random generator is needed, no deconvolution,
nothing clever: knowing that the noise exists, training with it, and waiting
for enough keystrokes.

## So is kloak enough?

It depends on how much an observer gets to see.

- **A login form, a password, a short message**: kloak helps a lot.
  Identification on a single 11-key sample falls from 48 % to 13 to 22 %.
- **A session**: a page that measures every keystroke while you write a
  comment or fill in a form sees hundreds to thousands of keystrokes. kloak
  buys some margin and no more. Linking two of your sessions together, which
  is how de-anonymisation actually works, is the averaging case.

The original README already says it in one sentence: kloak obfuscates your
typing behaviour, but does not make it similar to other users'. Random
jitter around your own rhythm leaves your rhythm in place. To really hide,
the output timing would have to stop depending on the input: release keys on
a fixed clock, or at a rate drawn independently of how you type. That costs
far more latency, and it is a different design.

## What it means for FidusAchates

I measured my own keystroke expert on the same data, one repetition per
segment. kloak at 100 ms takes it from an EER of 0.129 to 0.264 with a
template learnt without kloak, and to 0.233 if it learns under kloak. It is
hit harder than scaled Manhattan because it leans on holds, the feature kloak
damages most. Live, the expert judges windows of many keystrokes, so the
averaging result applies, but anyone who runs kloak should enrol with it on.

Two things matter more than the numbers:

- **Provenance.** The original kloak re-emits through `uinput`. The recorder
  marks such events as virtual (signal E01), so a kloak that was not there
  during bootstrap shows up as an unknown virtual keyboard. That is the right
  call: a user-space process re-timing every key is also what a hostile agent
  looks like.
- **A grab blinds the recorder.** Both versions take an exclusive grab on the
  physical keyboard. The Whonix version then injects through the compositor,
  not through `uinput`, so the recorder would simply see no keys while I
  type. It does not notice that today. The shell extension already reports
  activity that `evdev` does not see, which is the beginning of an answer, and
  I will treat "keyboard silent while the session is typing" as a signal of
  its own.

The other side of the question, an automaton that adds kloak-like jitter to
look human, is a different measurement (signals E02 to E04, E18) and I have
not run it yet.

## Limits

CMU is one password typed many times; free text spreads the same number of
keystrokes over many key pairs, so the break-even point moves (later for an
observer modelling each pair, earlier for one pooling them, as my expert
does). I modelled the schedule, not the binary: the event loop and the
compositor add their own jitter, much smaller than the delays here. Scaled
Manhattan is a weak detector by today's standards; a better one recovers more,
so the averaging figures are a floor for the observer, not a ceiling.
